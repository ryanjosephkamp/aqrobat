## Summary

Copying QR characters into editors can lose their layout. Codex built Aqrobat
with deterministic text/emoji generation, image and styled-text exports, a static
demo, private package/CLI, and an unpacked Make → Save → Insert extension.
Product 0.4.2 and its original downloads remain unchanged by the prose research.

The prose goal remains unsolved: Ryan reports that the earlier full PNG examples
fail both Samsung Camera and Samsung's dedicated Scan QR code tool. The prior
styled-prose and uniform-black ASCII techniques remain separate configured-reader
feasibility results, including three exact TXT-to-pixel proofs; these are not
normal-phone acceptance.

The new phase retains 101 text renderings and eight display views of earlier PNGs.
All 109 fail jsQR, default ZXing, and the retained baseline. Read-only diagnostics
find fragmented dark-region ink and unrelated locator geometry. Faint gray,
outlining, visible decorations, tighter leading, shrinking, blur, and ordinary
paragraph justification do not solve the tested cases.

## Verification

Current phase: 18/18 product unit tests, full formatting, Git whitespace/scope,
source/pixel custody, and read-only result reconciliation. The 109 candidate
views produce 327 failed exact-payload attempts. Fourteen conventional controls
pass all three probes (42 control attempts). Default ZXing receives only the QR
format restriction; no custom binarizer or downscale settings. Expected content
is compared afterward. No expected payload or matrix is supplied to independent
decoding, and no pixel repair is used.

Visible blur and browser resampling are explicit presentation experiments,
separate from native sharp text. Diagnostic binarization and source-matrix
coverage measurements never count as decoded output or feed acceptance readers.
The original three product download hashes match the earlier receipt. Previous
build/site/text-browser checks remain earlier disposable-copy results, not new
runs. The status file has exact PNG/native-HTML/checkpoint export bytes, no page
errors or automatic external requests, and fits a 390-pixel browser viewport.
These are browser checks, not physical-phone, clipboard, or email observations.

## Deviations

Strong blur exhausted the evidence reserve before retaining or decoding case 18;
faint text likewise stopped before case 4. The first decoration batch stopped
source-line fidelity before its first raster; its evidence is retained and a fresh
preformatted container corrected the harness. Sixteen planned text cases did not
reach decoding and are not counted as failed scans. Earlier executed sources and
raw HTML are preserved when formatting or harness code changed. No failed result
was removed or substituted. The final reconciliation retains the earlier 108-view
checkpoint as well as the complete 109-view receipt.

## Known issues

The later small-view replay check reproduces six of eight captured PNG hashes;
raw HTML/setContent equivalence remains an open harness issue. Original executed
HTML snapshots and authoritative retained PNGs remain preserved. These are
replay checks, not additional decoding attempts or an accepted portable rendering.

Readable, inconspicuous, meaningful prose with ordinary-reader and phone scanning
is still open. Faint letters hurt visibility; outlining hurts legibility; tiny
views cannot establish readable text. Prior successful ASCII word forms are
fabricated and repetitive and require compatible typography/configured readers.
The next bounded objective is actual glyph/finder geometry under ordinary
thresholding, with readable native letters and independent default-reader gates.

No new phone or physical-print tests. Exact earlier phone-case denominator and
viewing conditions are unknown. Actual Gmail/received-email, native clipboard,
and owner installed-extension acceptance remain separate product work. The emoji
atlas is still deferred. This checkpoint is not a completed-prose claim.
